TalentIQ — Guia de Melhorias

Avaliação crítica da arquitectura, segurança, performance e qualidade de produto, com recomendações accionáveis ordenadas por prioridade.

📅 Julho 2026 🔒 Versão 0.2.0 Web ⚙️ Django 6 · PostgreSQL · Railway
Sumário. O TalentIQ tem uma base técnica correcta e resolve um problema real no mercado de recrutamento em saúde. O fluxo guiado de 7 passos por vaga é um diferenciador genuíno. No entanto, antes de crescer a base de clientes, existem dois riscos críticos de segurança que expõem dados de candidatos à internet sem qualquer autenticação. A correção imediata dessas vulnerabilidades deve preceder qualquer nova funcionalidade.

Segurança
Crítico — Actuar Hoje
Vulnerabilidades activas que expõem dados de candidatos sem autenticação
🔴 URLs de debug expostas em produção Crítico

As seguintes URLs estão acessíveis a qualquer pessoa na internet sem qualquer autenticação:

/accounts/debug-login/   → mostra hash da password e estado do utilizador
/accounts/debug-auth/    → confirma credenciais via Django authenticate()
/accounts/reset-admin/   → repõe a password do admin sem autenticação
/accounts/auto-login/    → faz login como admin sem credenciais

Num sistema com dados pessoais de candidatos, isto é uma violação de dados e pode ser ilegal sob a lei moçambicana de protecção de dados.

Solução: Remover estas views e URLs completamente antes de partilhar o link com clientes. As ferramentas de debug foram úteis durante o desenvolvimento mas não têm lugar em produção.

🔴 Sem rate limiting no login Crítico

O endpoint /accounts/login/ não tem limite de tentativas. Um atacante pode tentar milhares de passwords por minuto sem ser bloqueado.

Solução: Instalar django-ratelimit e decorar a view de login:

pip install django-ratelimit

# accounts/views.py
from ratelimit.decorators import ratelimit

@ratelimit(key='ip', rate='10/m', method='POST', block=True)
def login_view(request):
    ...
🟡 Sem HTTPS forçado em produção Alto

O app não força HTTPS explicitamente nas definições Django. O Railway serve HTTPS, mas sem a configuração correcta o Django pode aceitar ligações HTTP.

# settings.py
SECURE_SSL_REDIRECT = True

Autenticação
Alto
O mecanismo de seed_admin cria uma dependência frágil entre arranque do servidor e credenciais
seed_admin repõe a password em cada restart Alto

O comando seed_admin corre em cada startup do Railway e redefine sempre a password do admin para o valor de ADMIN_PASSWORD. Isto foi a causa do problema recorrente de login.

Solução recomendada: Só repor a password se o utilizador não existir ainda.

# seed_admin.py
user, created = User.objects.get_or_create(email=email)
if created:
    user.set_password(password)  # só na criação inicial
user.is_active = True
user.save()

Após a primeira criação, gerir a password exclusivamente via painel de utilizadores ou django-admin.

Sem recuperação de password self-service Alto

Se um utilizador esquece a password, depende do admin para a repor. Em contexto multi-cliente, o admin pode não estar disponível.

Solução: Activar o flow nativo do Django (PasswordResetView) com envio de email. Requer configuração SMTP (ex: SendGrid, Mailgun) via variável de ambiente.

# settings.py
EMAIL_BACKEND = 'django.core.mail.backends.smtp.EmailBackend'
EMAIL_HOST = os.environ.get('EMAIL_HOST')
EMAIL_PORT = 587
EMAIL_USE_TLS = True
EMAIL_HOST_USER = os.environ.get('EMAIL_HOST_USER')
EMAIL_HOST_PASSWORD = os.environ.get('EMAIL_HOST_PASSWORD')
Autorização (RBAC)
Alto
As funções existem no modelo mas não estão aplicadas nas views
Qualquer utilizador autenticado tem acesso total Alto

Os roles Admin / Recrutador / Visualizador estão definidos no modelo User mas nenhuma view verifica o role antes de permitir a acção. Um Visualizador consegue actualmente eliminar vagas ou exportar dados.

Solução: Criar um decorator de permissão e aplicá-lo a cada view.

# accounts/decorators.py
from functools import wraps
from django.http import HttpResponseForbidden

def role_required(*roles):
    def decorator(view_func):
        @wraps(view_func)
        def wrapper(request, *args, **kwargs):
            if not request.user.is_authenticated:
                return redirect('/accounts/login/')
            if request.user.role not in roles:
                return HttpResponseForbidden("Acesso negado.")
            return view_func(request, *args, **kwargs)
        return wrapper
    return decorator

# Uso nas views:
@role_required('admin', 'recruiter')
def vaga_delete(request, pk):
    ...
Performance e Escalabilidade
Alto
Gargalos que se tornam críticos a partir de ~100 candidatos activos
Análise IA bloqueia o request HTTP Alto

Quando o utilizador clica "Analisar com IA", o servidor Django espera pela resposta da API Grok (pode demorar 10–30 segundos) antes de devolver a página. O Gunicorn tem um timeout de 30s — chamadas lentas causam erro 502.

Solução: Mover a análise IA para uma task assíncrona com Celery + Redis. A UI mostra um spinner e polling até a task terminar.

pip install celery redis django-celery-results

# tasks.py
from celery import shared_task

@shared_task
def analisar_cv_async(candidato_id):
    candidato = Candidato.objects.get(pk=candidato_id)
    resultado = analisar_cv_com_ia(candidato.cv_path)
    candidato.perfil_completo = resultado
    candidato.save()

# views.py
task = analisar_cv_async.delay(candidato.pk)
return JsonResponse({"task_id": task.id})
Listas sem paginação Médio

As views de candidatos e vagas carregam todos os registos da base de dados em memória. Com 500+ candidatos, as páginas ficarão lentas e o servidor pode atingir limites de memória no Railway.

Solução: Usar o Paginator nativo do Django.

# views.py
from django.core.paginator import Paginator

candidatos = Candidato.objects.filter(org=org).order_by('-created_at')
paginator = Paginator(candidatos, 25)  # 25 por página
page_obj = paginator.get_page(request.GET.get('page'))
Sem cache nas queries repetidas Médio

O dashboard e o ranking geral fazem queries complexas a cada page load, mesmo quando os dados não mudaram. Em Railway, o plano gratuito tem limites de CPU.

Solução de curto prazo: Cache por view com cache_page. Cache com Redis (mesmo Redis do Celery) para longa duração.

from django.views.decorators.cache import cache_page @cache_page(60 * 5) # cache 5 minutos def ranking_geral(request): ...
Motor de Scoring
Médio
O algoritmo determinístico actual tem limitações que reduzem a precisão
Correspondência de competências por palavras-chave exactas Médio

O motor actual compara competências como strings. "Gestão de Projectos" e "Project Management" são tratados como não correspondentes, mesmo sendo equivalentes. O mesmo acontece com variações como "VIH" vs "HIV".

Solução de curto prazo: Tabela de sinónimos configurável por domínio (saúde, RH, etc.).

Solução de médio prazo: Usar embeddings de texto (ex: sentence-transformers) para calcular similaridade semântica em vez de correspondência exacta.

from sentence_transformers import SentenceTransformer, util model = SentenceTransformer('paraphrase-multilingual-MiniLM-L12-v2') def score_competencias(requeridas, candidato): emb_req = model.encode(requeridas) emb_cand = model.encode(candidato) scores = util.cos_sim(emb_req, emb_cand) return float(scores.max(dim=1).values.mean())
Score não recalcula após edição de perfil Médio

Quando o utilizador edita o perfil de um candidato (corrige competências, altera anos de experiência), o score não é recalculado automaticamente. O utilizador tem de se lembrar de voltar à página de scoring e recalcular manualmente.

Solução: Usar o signal post_save do Django para marcar o score como desactualizado e recalcular automaticamente (ou mostrar um aviso).

from django.db.models.signals import post_save @receiver(post_save, sender=Candidato) def invalidar_score(sender, instance, **kwargs): instance.score_fit = None Candidato.objects.filter(pk=instance.pk).update(score_fit=None)
Observabilidade
Médio
O app falha silenciosamente — erros em produção não são detectados
Sem captura de erros em produção Alto

Quando o app lança uma excepção em produção (timeout da API IA, erro de base de dados, bug de código), o utilizador vê um erro genérico e tu não és notificado. Sem Sentry ou equivalente, os erros são invisíveis.

Solução: Integrar Sentry (plano gratuito é suficiente para começar).

pip install sentry-sdk # settings.py import sentry_sdk sentry_sdk.init( dsn=os.environ.get("SENTRY_DSN"), traces_sample_rate=0.1, environment="production" if not DEBUG else "development", )

Adicionar SENTRY_DSN às variáveis de ambiente no Railway.

Sem métricas de uso Médio

Não é possível saber quantas vagas foram criadas esta semana, quantos candidatos foram analisados com IA, onde os utilizadores abandonam o processo, ou qual o tempo médio de cada passo.

Solução de baixo custo: Adicionar um campo created_at e updated_at a todos os modelos (se ainda não existir) e construir um dashboard de métricas interno no painel de Sistema. Para análise mais rica: Posthog (open-source, auto-hospedável).

Testes Automatizados
Médio
A ausência de testes faz com que cada deploy seja um risco de regressão
Nenhum teste automatizado Médio

O bug do scoring silencioso (HTMX) e os caracteres garrafados no relatório Word são sintomas directos da ausência de testes — foram descobertos por acidente pelo utilizador, não por um pipeline de CI.

Prioridade dos primeiros testes:

  • Login com credenciais correctas e incorrectas
  • Criação de vaga com campos obrigatórios
  • Upload de CV e extracção de perfil
  • Cálculo de score determinístico (resultado esperado para inputs conhecidos)
  • Exportação Excel e Word (ficheiro gerado sem erro)
  • Isolamento multi-tenant (utilizador A não vê dados da org B)

Melhorias de Produto
Futuro
Funcionalidades que aumentam o valor para o cliente mas que não são urgentes
API REST para integrações e mobile Futuro

Sem uma API, o TalentIQ não pode ser integrado com sistemas de RH existentes (ex: DHIS2, sistemas de payroll), não permite uma app móvel nativa e não permite que clientes exportem dados para os seus próprios sistemas.

Stack recomendada: Django REST Framework + SimpleJWT para autenticação por token. Documentação automática com drf-spectacular (OpenAPI/Swagger).

Auditoria de acções (Audit Log) Futuro

Em contexto de saúde pública com múltiplos utilizadores, é importante saber quem alterou o estado de um candidato, quem exportou um relatório, ou quem eliminou uma vaga. Especialmente relevante para conformidade com doadores internacionais (PEPFAR, GF, etc.).

Solução: django-auditlog ou modelo AuditEvent próprio com user, action, object_type, object_id, timestamp.

Portal do candidato (submissão de candidaturas online) Futuro

Actualmente os CVs são carregados manualmente pelo recrutador. Um portal público onde os candidatos submetem os seus próprios CVs eliminaria este passo manual e tornaria o sistema mais escalável.

Cada vaga teria um link público de candidatura (/candidatar/vaga-slug/) sem login. O candidato submete nome, email e CV. O recrutador vê as candidaturas na plataforma e decide quais analisar com IA.
